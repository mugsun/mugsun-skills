# mugsun-audit：代码审查

## 触发词

审查、审一下、code review、review 这个提交、能不能合、看下这个分支。

## 必问参数

1. 审查范围：仓库和提交区间（如 `base..head`），或分支名。
2. 改动类型：普通代码、UI、文档，还是敏感改动（见下）。
3. 是否已有 CI 结果：有的话给出运行链接或结论。

## 默认值

- 只读审查：不改代码、不提交、不推送。
- 结论三选一：可合、改后合、不可合，并写明审查的 SHA。
- 每条问题分级：
  - 阻塞：不改不能合，如正确性错误、安全问题、修改了已发布的迁移、缺测试导致行为无法验证。
  - 建议：应该改，可以下一个提交改。
  - 可选：风格或小优化，作者自己决定。
- 每条写清 `文件:行号`、问题是什么、怎么改。

## 不适用于

- 替作者直接改代码或代为提交。
- 只有文档、文案、样式或 CHANGELOG 的改动：CI 绿即可（安全相关文档除外，先给安全官看），不必走完整审查。
- 删除或下线功能的决定：要先问项目负责人。

## 步骤

1. 列出区间内的提交和改动文件，先看提交信息是否符合 Conventional Commits。
2. 逐文件读 diff，对照所在仓库的 `AGENTS.md`：分层、命名、实体基类、租户与数据权限、迁移规则。
3. 重点检查：
   - 跨租户查询是否只用了 `TenantContext.ignore` / `execute`，范围是否最小；
   - 新表要不要数据权限，要的话是否登记了受控表并加了 `@DataScope`；
   - 已发布的迁移有没有被改动（哪怕一个字节）；新迁移三套方言是否同号；
   - 新接口有没有权限注解，请求体里的审计字段是否被清洗；
   - 有没有测试覆盖改动的行为。
4. UI 改动：必须看到四种状态的截图或亲自跑一遍——空表单提交、英文、暗色、390px 宽。只读代码不算通过，缺截图记为阻塞。
5. 敏感改动要同时请安全审查，两边都通过才能合：登录与验证码、认证鉴权、租户隔离、密钥与加密、新增依赖、公开 API、CI workflow 与门禁规则。
6. 汇总结论。

```
阻塞

- S1 ……

可选
- O1 ……

```
